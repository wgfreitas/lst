## Raciocínio (passos 1 a 5)

**1. Pontos de comunicação**

| Ponto | De → para |
|---|---|
| P1 | ambiente/`.env` → `Settings` (validação) |
| P2 | CLI → pipeline (arquivo de log, `--dry-run`, código de saída) |
| P3 | pipeline → requisição HTTP (endpoint, cabeçalho, corpo, timeout) |
| P4 | cliente HTTP ↔ servidor (rede, status HTTP, novas tentativas, degradação) |
| P5 | resposta → interpretação (envelope, JSON do `content`, tolerâncias) |
| P6 | interpretação → relatório (stdout); erros → stderr |

**2. Falhas e valores que precisam atravessar cada ponto**

- **P1.** Falhas possíveis: chave ausente; valor fora da faixa ou de tipo errado; modo desconhecido. Valores: todas as `LLM_*`, sem herdar o `.env` ou o shell do desenvolvedor.
- **P2.** Falhas possíveis: arquivo inexistente; `--dry-run` que contata o provedor ou exige a chave. Valor: o nome do arquivo na mensagem.
- **P3.** Falhas possíveis: valor aceito mas não aplicado (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_MAX_TOKENS`, `LLM_TIMEOUT_SECONDS`, `LLM_STRUCTURED_MODE`); chave no corpo; amostras acima do limite. O que precisa chegar à requisição: `Authorization: Bearer <chave>`, `model`, `max_tokens`, `response_format` e o timeout. O que não pode sair da máquina: a chave no corpo e mais de 3 IPs, 3 usuários ou 3 linhas por evento.
- **P4.** Falhas possíveis: conexão recusada, conexão interrompida, timeout, 401, 404, 400 por `response_format` ou por outro motivo, 429, 5xx e número errado de tentativas. Valores: `1 + LLM_MAX_RETRIES` tentativas e a cadeia json_schema → json_object → sem `response_format`.
- **P5.** Falhas possíveis: corpo vazio, `content` vazio, resposta não-JSON, campo ausente e `severity` fora da lista. Também é falha tratar como inválido um formato tolerado (cercas, texto em volta, maiúsculas). Valor: `1 + LLM_PARSE_RETRIES` tentativas.
- **P6.** Falhas possíveis: evento descartado em silêncio, relatório não gerado por causa de um evento inválido, traceback ou mensagem genérica. Valores: `explanation` e `next_action` no relatório; a causa no stderr.

**3. Comportamento esperado**

O contrato define, e os testes verificam:
- os códigos 0/1/2 e as quatro mensagens documentadas;
- zero requisições sem chave, com configuração inválida, com arquivo inexistente e em `--dry-run`;
- uma chamada por evento;
- novas tentativas só para 5xx e 429;
- degradação só no modo `auto` e só por 400 de `response_format`;
- 200 inválido → nova requisição e depois a seção "## Eventos não explicados", com o relatório gerado.

O contrato não define, e por isso viraram lacunas sem asserção:
- o desfecho depois de esgotar as novas tentativas;
- o desfecho de falha de rede, de 404 e de um 400 que não degrada;
- os tipos de exceção de `run_pipeline`;
- se timeout e falhas de rede contam em `LLM_MAX_RETRIES`.

Nesses testes verifico só o que está definido: número de tentativas, ausência de degradação e ausência de exceção interna. O desfecho fica isolado por `contextlib.suppress` ou por uma asserção que só vale se houver saída de erro.

**4. Casos de borda**

- **Faixas fechadas.** Mínimo e máximo são aceitos e aplicados:
  - `max_tokens` 64 e 4096 aparecem na requisição;
  - timeout 1.0 e 300.0 contra um servidor lento simulado;
  - `LLM_MAX_RETRIES` 0 e 5 contra 503;
  - `LLM_PARSE_RETRIES` 0 e 3 contra resposta inválida.
- **Primeiro valor fora da faixa.** -1/6, -1/4 e 63/4097. O float não tem um "primeiro" valor exato, então usei 0.9 e 300.1. Somam-se um modo desconhecido e um tipo inválido.
- **Respostas vazias.** `content` igual a `""` e corpo 200 vazio.

**5. Requisito de qualidade nas saídas de erro**

O helper `assert_clean_error` exige três coisas:
- (a) que a CLI tenha saído de propósito (`SystemExit`). O `CliRunner` captura exceções não tratadas e devolve código 1, então o código sozinho não prova que o erro foi tratado.
- (b) nenhum marcador de exceção interna na saída: `Traceback`, `httpx`, `ValidationError` ou nomes de classes de exceção.
- (c) a causa nomeada no stderr: a variável (`LLM_API_KEY`, `LLM_TIMEOUT_SECONDS`, a variável fora da faixa, `LLM_BASE_URL` em falha de rede), o status (`401`, `400`, `404`) ou o nome do arquivo.

**Premissas do código**
- pytest-asyncio em modo `auto`, como no exemplo.
- Click ≥ 8.2, que separa `result.stderr`.
- Os testes de CLI são síncronos, porque a CLI cria o próprio event loop.
- O timeout é aplicado via `httpx`. Como o respx não faz I/O real, o servidor lento simulado lê o timeout que o LST pôs em `request.extensions["timeout"]`.

def chat_completion(content: str) -> httpx.Response:

def http_error(status: int, message: str, param: str | None = None) -> httpx.Response:
    """Erro no formato da API OpenAI; Retry-After: 0 evita espera real nas novas tentativas."""
    return httpx.Response(
        status,
        headers={"Retry-After": "0"},
        json={
            "error": {
                "message": message,
                "type": "invalid_request_error",
                "param": param,
                "code": None,
            }
        },
    )


def replies(*first: Reply, then: Reply = partial(chat_completion, VALID_REPLY)) -> Handler:
    """Servidor que devolve as respostas `first` em ordem e, depois, `then` indefinidamente."""
    pending = list(first)

    def handler(request: httpx.Request) -> httpx.Response:
        return (pending.pop(0) if pending else then)()

    return handler


def always(reply: Reply) -> Handler:
    """Servidor que devolve sempre uma resposta nova produzida por `reply`."""
    return lambda request: reply()


def rejects_response_format(request: httpx.Request) -> httpx.Response:
    """Provedor sem saída estruturada: 400 com param=response_format sempre que o campo vier."""
    if "response_format" in json.loads(request.content):
        return http_error(400, "response_format is not supported by this model", "response_format")
    return chat_completion(VALID_REPLY)


def slow_server(delay: float) -> Handler:
    """Servidor que leva `delay` segundos: estoura se o timeout de leitura da requisição for menor.

    O respx não faz I/O real, então o timeout do httpx nunca dispara sozinho; o servidor
    simulado usa o timeout que o LST de fato configurou na requisição.
    """

    def handler(request: httpx.Request) -> httpx.Response:
        read_timeout = request.extensions.get("timeout", {}).get("read")
        if read_timeout is not None and read_timeout < delay:
            raise httpx.ReadTimeout("servidor lento simulado", request=request)
        return chat_completion(VALID_REPLY)

    return handler


def payloads(route: respx.Route) -> list[dict[str, Any]]:
    """Corpos JSON de todas as requisições recebidas pela rota."""
    return [json.loads(call.request.content) for call in route.calls]


def format_type(payload: dict[str, Any]) -> str | None:
    """Tipo do response_format enviado, ou None quando o campo não foi enviado."""
    return (payload.get("response_format") or {}).get("type")


def first_event_attempts(route: respx.Route) -> list[dict[str, Any]]:
    """Tentativas do 1º evento: chamadas iniciais consecutivas com a mesma mensagem `user`.

    Conta novas tentativas sem supor se o LST aborta ou segue para o evento seguinte.
    """
    sent = payloads(route)
    assert sent, "nenhuma requisição chegou ao provedor"
    first = sent[0]["messages"][-1]["content"]
    return list(itertools.takewhile(lambda p: p["messages"][-1]["content"] == first, sent))


def assert_no_internal_exception(result: Result) -> None:
    """Requisito da equipe: nenhuma exceção Python vaza para o analista.

    O CliRunner captura exceções não tratadas e devolve código 1; por isso exige-se que a
    CLI tenha saído de propósito (SystemExit) ou concluído sem exceção.
    """
    assert result.exception is None or isinstance(result.exception, SystemExit), (
        f"exceção não tratada na CLI: {result.exception!r}"
    )
    for marker in INTERNAL_MARKERS:
        assert marker not in result.output, f"exceção interna exposta ao analista: {marker!r}"


def assert_clean_error(result: Result, *causes: str) -> None:
    """Requisito da equipe: saída de erro tratada, sem exceção interna, que nomeia a causa."""
    assert result.exit_code != 0, "era esperada uma saída de erro"
    assert_no_internal_exception(result)
    for cause in causes:
        assert cause in result.stderr, f"a mensagem de erro não nomeia a causa {cause!r}"

async def test_only_sampled_log_data_leaves_the_machine(tmp_path: Path) -> None:
    """Ponto: pipeline → requisição. Regra: saem só o template e amostras de no máximo
    3 IPs, 3 usuários e 3 linhas originais por evento.

    O log é o fixture com cada linha repetida para 10 IPs (203.0.113.0/24) e 10 usuários
    sintéticos, para que os eventos tenham mais de 3 de cada.
    """
    lines = FIXTURE.read_text(encoding="utf-8").splitlines()
    amplified = [
        variant
        for line in lines
        for variant in [line]
        + [
            SSH_USER.sub(rf"\1 lstuser{k:02d} from", IPV4.sub(f"203.0.113.{k}", line))
            for k in range(1, 11)
        ]
    ]
    log = tmp_path / "amplified.log"
    log.write_text("\n".join(amplified) + "\n", encoding="utf-8")
    users = {m.group(2) for line in amplified for m in SSH_USER.finditer(line)}

    with respx.mock(assert_all_called=True) as router:
        route = router.post(ENDPOINT).mock(return_value=chat_completion(VALID_REPLY))
        await run_pipeline(log, make_settings())

    for payload in payloads(route):
        sent = "\n".join(str(m["content"]) for m in payload["messages"])
        sent_lines = {line for line in amplified if line.strip() and line in sent}
        assert len(sent_lines) <= 3, "mais de 3 linhas originais saíram da máquina"
        rest = sent
        for line in sent_lines:
            rest = rest.replace(line, " ")
        assert len(set(IPV4.findall(rest))) <= 3, "mais de 3 IPs na amostra"
        sampled_users = {u for u in users if re.search(rf"\b{re.escape(u)}\b", rest)}
        assert len(sampled_users) <= 3, "mais de 3 usuários na amostra"

## Lacunas do contrato

1. **Esgotamento das novas tentativas (5xx/429).** "Depois de `1 + LLM_MAX_RETRIES` falhas, o LST aborta com código 1 ou lista o evento em 'Eventos não explicados' e segue? Com qual mensagem?"
2. **Falhas de rede.** "Conexão recusada, DNS, TLS e conexão interrompida contam como transitórias para `LLM_MAX_RETRIES`? Com qual código de saída e mensagem?"
3. **Semântica do timeout.** "`LLM_TIMEOUT_SECONDS` é o limite total da chamada ou um limite por operação (connect/read do httpx)? Um timeout gera nova tentativa?"
4. **Espera entre tentativas.** "Há backoff? O `Retry-After` do 429/503 é respeitado, e com que teto?" (Isso define a duração da suíte com `LLM_MAX_RETRIES=5`.)
5. **Outros 4xx.** "Qual o desfecho de 403, 404, 413 e 422? Um 403 conta como 'erro de autenticação'?"
6. **400 que vira erro.** "No modo fixado, e no `auto` quando o 400 não é de `response_format`, qual o código de saída e a mensagem?"
7. **Detecção do 400 de `response_format`.** "O LST decide pelo `error.param`, pelo texto da mensagem ou por um código? O formato de erro de cada provedor (Ollama Cloud, OpenRouter, OpenAI) foi validado?"
8. **Memória da degradação.** "Depois de degradar no 1º evento, os eventos seguintes recomeçam em `json_schema` ou usam o modo que funcionou?"
9. **Exceções de `run_pipeline`.** "Que tipos ela propaga em cada erro operacional? Há uma hierarquia própria do LST?"
10. **Relatório parcial.** "Se um erro operacional ocorre no 2º evento, o relatório dos eventos já explicados vai para o stdout?"
11. **Formato de 'Eventos não explicados'.** "Como cada evento é identificado ali (template, ocorrências, motivo, tentativas)?" Sem essa definição, não é possível provar que os 3 eventos foram listados.
12. **`severity` no relatório.** "A severidade aparece no relatório? Em que seção e em que formato?"
13. **Envelope inválido com 200.** "`choices` vazio, `content` null, corpo HTML ou `finish_reason: "length"` contam como resposta inválida (nova requisição) ou como erro?"
14. **Campos extras.** "O contrato diz 'exatamente' três campos. Um JSON com um campo a mais é inválido ou tolerado?"
15. **Chave vazia e vazamento.** "`LLM_API_KEY` vazia ou só com espaços equivale a ausente? Mensagens de erro e logs podem conter a chave ou trechos do log?"
16. **Validação da configuração.** "Qual o texto da mensagem para valor fora da faixa ou de tipo inválido? A faixa de `LLM_TIMEOUT_SECONDS` tem precisão definida (0.99 é inválido)? `LLM_STRUCTURED_MODE` aceita maiúsculas?"
17. **Precedência.** "Se a variável existe no ambiente e no `.env`, qual vale?"
18. **Saída do `--dry-run`.** "O que o `--dry-run` imprime e com que código termina?"
19. **Amostras.** "Como as 3 amostras são escolhidas (as primeiras, as mais frequentes)? As linhas vão íntegras ou podem ser truncadas ou mascaradas? Hostnames e portas também têm limite?"
